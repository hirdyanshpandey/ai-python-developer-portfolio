MCP security in 2026:
from connection to production controls.

A successful tool call proves connectivity. Production readiness needs evidence about who can call it, what it can reach, and how its effects are bounded.

BackendKit editorial · Published 18 November 2026 · Sources checked 18 November 2026 · 5 minute read

What this article is

A source-based implementation guide with an original application scenario and suggested tests. It is not a new vulnerability disclosure or a benchmark. Examples below are design exercises, not claims about a tested deployment. Prepared with AI assistance.

1. Make the token boundary explicit

The official MCP guidance prohibits token passthrough: a server must not accept a token intended for another resource and forward it downstream. Authentication to your MCP server and access to an upstream API are separate boundaries. See source 1.

Application exercise: imagine an invoice assistant with a read-only lookup tool and a write tool that updates vendor details. Draw both credential paths before writing handlers. For each path, record the intended resource, allowed operation and identity used for tenant selection. A token being valid somewhere is insufficient evidence that this operation is permitted here.

2. Review the complete tool definition

OWASP recommends checking the full definition, including schemas and annotations, and reviewing changes. It also distinguishes metadata integrity from runtime enforcement: a label such as readOnlyHint does not constrain server behavior. See source 2.

Our implementation suggestion: keep a reviewed definition snapshot alongside your release notes. Have the release process show a readable diff. Ask reviewers whether a new parameter changes the effect of a call, rather than reviewing only whether its description looks familiar. This is a change-management technique, not proof that a package is trustworthy.

3. Use an invoice workflow as a design exercise

Here is a concrete review worksheet for the hypothetical assistant. These are proposed acceptance criteria, not protocol requirements.

OperationReview questionProposed evidence
Read invoiceCan tenant A request tenant B’s record?A denied cross-tenant test using two separate identities.
Update vendorDoes the application check the exact proposed change?A test where the vendor ID changes after review and execution is refused.
Import CSVWhat happens to malformed rows?A fixture with duplicate headers and inconsistent widths, rejected before persistence.
Retry a writeCan a repeated request duplicate a business effect?A replay test against the application’s idempotency design.

These tests belong at the service boundary. A natural-language instruction to behave carefully does not demonstrate that the handler enforces its contract.

4. Turn source guidance into release tests

The MCP security guide also covers SSRF during OAuth discovery and requires authorization checks for application-owned state handles; possession of a handle is not authentication. Legacy session-based deployments need version-specific treatment. See source 1.

OWASP additionally discusses least privilege, validating tool inputs and outputs, isolation, sensitive-action controls and redacted audit logs. See source 2.

Suggested release habit: choose one negative test for each boundary you actually expose. Keep the input, expected denial, observed outcome and implementation version together. When a release adds a new URL-fetching path or a new writable operation, update that evidence. Passing a static configuration check alone is not the same as running these behavioral tests.

Frequently asked questions

Does connecting through MCP make a tool safe?

Connectivity does not establish application authorization. Inspect the service’s actual behavior and the boundaries relevant to your deployment.

Is this a security certification?

No. It is a focused review guide. The worksheet is a starting point for your own threat model and tests.
